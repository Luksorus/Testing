# Практическая работа №2

**Тема:** разработка плана тестирования.

## 1. Цель работы

Изучить элементы плана тестирования и разработать его фрагмент для веб-приложения: распределить проверки по уровням, оценить риски и определить содержание основных секций тест-плана.

## 2. Общая информация

| Параметр | Значение |
| --- | --- |
| Объект | The Internet, раздел Checkboxes |
| Адрес | <https://the-internet.herokuapp.com/checkboxes> |
| Основа планирования | [Документация практической работы №1](../practice-01/README.md): Checklist, Acceptance Sheet и Test Cases |
| Организация работы | Индивидуальная работа; подготовка документации и выполнение проверок относятся к роли тестировщика |
| Результат | Фрагмент тест-плана: проверки по уровням, оценка рисков, описание секций и критериев завершения |

Продолжается работа с тем же приложением, которое использовано в первой практике. Страница содержит два независимых флажка: `checkbox 1` и `checkbox 2`. В первой работе исходным состоянием было `(0, 1)`, где `0` означает снятый флажок, а `1` — установленный. В паре первым указывается состояние `checkbox 1`.

Основа Smoke — базовые проверки CL-01, CL-04 и CL-05 и сценарии TC-01–TC-03 первой работы. Составной пункт CL-01 разделен на открытие страницы и доступность каждого флажка, чтобы получить пять проверок для небольшого модуля. Остальные пункты прежнего чеклиста используются для основных и расширенных сценариев.

Проверки ниже запланированы для следующего прогона. Статусы из первой работы не являются результатами выполнения нового плана. Ранее обнаруженный BUG-01 — отсутствие переключения при клике по подписям — учитывается в расширенных проверках и должен быть проверен повторно.

## 3. Задание 1. Уровни тестирования

Перед каждым сценарием следует отдельно установить заданное начальное состояние непосредственными кликами по квадратам флажков. Нельзя рассчитывать на результат предыдущего сценария. Ожидание переключения по тексту подписи основано на базовых проверках чекбоксов из методички первой работы.

### 3.1. Smoke Test

| Уровень | № | Пример проверки и ожидаемый результат | Комментарий: почему этот уровень |
| --- | --- | --- | --- |
| Smoke | S-01 | Открыть адрес раздела. Отображается страница Checkboxes, а не сообщение о недоступности | Без загрузки страницы дальнейшие проверки невозможны; основа — CL-01, TC-01 |
| Smoke | S-02 | Проверить первый флажок: квадрат и подпись `checkbox 1` видны, элемент доступен для взаимодействия | Отсутствие одного из двух основных элементов делает модуль неполным; основа — CL-01 |
| Smoke | S-03 | Проверить второй флажок: квадрат и подпись `checkbox 2` видны, элемент доступен для взаимодействия | Второй элемент также необходим для работы модуля; основа — CL-01 |
| Smoke | S-04 | При `(0, 1)` нажать на квадрат первого флажка. Получается `(1, 1)` | Минимальная проверка возможности установки флажка; основа — CL-04, TC-02 |
| Smoke | S-05 | При `(1, 1)` нажать на квадрат второго флажка. Получается `(1, 0)` | Минимальная проверка возможности снятия флажка; основа — CL-05, TC-03 |

### 3.2. Critical Path Test

| Уровень | № | Пример проверки и ожидаемый результат | Комментарий: почему этот уровень |
| --- | --- | --- | --- |
| Critical Path | CP-01 | При `(0, 1)` установить первый флажок и снять его повторным кликом по квадрату. Переходы: `(0, 1) → (1, 1) → (0, 1)` | Основной маршрут выбора и отмены первого значения; CL-04, CL-06 |
| Critical Path | CP-02 | При `(0, 1)` снять второй флажок и установить его повторным кликом по квадрату. Переходы: `(0, 1) → (0, 0) → (0, 1)` | Основной маршрут изменения второго значения; CL-05 и симметричная проверка установки |
| Critical Path | CP-03 | При `(0, 0)` поочередно установить оба флажка. Переходы: `(0, 0) → (1, 0) → (1, 1)` | Типичный сценарий множественного выбора; установка второго не должна снимать первый; CL-07 |
| Critical Path | CP-04 | При `(1, 1)` поочередно снять оба флажка. Переходы: `(1, 1) → (0, 1) → (0, 0)` | Пользователь отменяет весь выбор; ни один флажок не должен быть принудительно установлен; CL-07 |
| Critical Path | CP-05 | При `(1, 0)` установить второй флажок, затем снять первый. Переходы: `(1, 0) → (1, 1) → (0, 1)` | Типичный маршрут замены выбранного набора с проверкой независимости состояний; CL-07 |

### 3.3. Extended Test

| Уровень | № | Пример проверки и ожидаемый результат | Комментарий: почему этот уровень |
| --- | --- | --- | --- |
| Extended | E-01 | При `(0, 1)` нажать на текст `checkbox 1`, не затрагивая квадрат. Ожидается `(1, 1)` | Дополнительный способ управления; повторная проверка первого проявления BUG-01; CL-11 |
| Extended | E-02 | При `(0, 1)` нажать на текст `checkbox 2`, не затрагивая квадрат. Ожидается `(0, 0)` | Дополнительный способ управления; повторная проверка второго проявления BUG-01; CL-12 |
| Extended | E-03 | При `(0, 0)` перевести фокус на первый флажок, нажать Space, затем Tab и Space. Ожидается `(1, 0) → (1, 1)`; фокус переходит ко второму флажку | Альтернативный маршрут без мыши проверяет клавиатурное управление и порядок фокуса; CL-08–CL-10 |
| Extended | E-04 | При `(1, 1)` обновить страницу. Страница загружается, ожидаемое базовое состояние — `(0, 1)` | Проверяется повторная инициализация; ожидание основано на TC-10 первой работы, а не на требовании сохранять пользовательский выбор; CL-13 |
| Extended | E-05 | Проверить страницу при ширине области 1280 px и 375 px, затем при масштабе 200%. Оба флажка и подписи читаемы, не перекрываются и доступны; допустима необходимая прокрутка | Проверка граничных условий отображения, оставшаяся невыполненной в первой работе; CL-02, CL-14 |

Всего запланировано **15 проверок: по 5 на каждый уровень**. Уровни описывают глубину проверки: Smoke подтверждает минимальную работоспособность, Critical Path — законченные пользовательские маршруты, Extended — дополнительные способы взаимодействия и условия. Частичное повторение действий между уровнями допустимо: цель и полнота сценариев различаются.

Для E-04, если поведение продукта изменилось, сначала следует уточнить требование к сохранению состояния. Отличие от прежнего поведения без утвержденного требования фиксируется как вопрос, а не автоматически объявляется дефектом.

## 4. Задание 2. Оценка рисков

Вероятности ниже являются экспертными оценками для учебного плана, а не статистикой отказов. Для приоритизации используется шкала: вероятность — низкая (1), средняя (2), высокая (3); влияние — низкое (1), среднее (2), высокое (3). Оценка угрозы равна произведению вероятности и влияния: 1–2 — низкая, 3–4 — средняя, 6–9 — высокая.

### R-01. Недоступность внешнего тестового окружения

| Поле | Описание |
| --- | --- |
| Риск: в чем суть? | Учебный сайт может оказаться недоступен из-за сбоя сервера, сети или ошибки сертификата; тип риска — технический |
| Вероятность | Средняя — окружение внешнее и не управляется тестировщиком; частота отказов не измерялась |
| Последствия | Невозможно открыть страницу и выполнить браузерные проверки; влияние высокое, оценка угрозы `2 × 3 = 6` — высокая |
| Как не допустить | До основного прогона проверить открытие URL и исправность своего подключения; заранее подготовить документацию и начальные состояния. Эти меры позволяют раньше обнаружить проблему, но не гарантируют доступность внешнего сервиса |
| Что делать, если наступил | Зафиксировать URL и текст ошибки, проверить подключение, повторить попытку после восстановления доступа. Недоступные проверки отметить Blocked. Если доступ не восстановлен, представить подготовленный план и согласовать перенос прогона; локальная копия допустима только как отдельно обозначенное окружение, ее результаты нельзя выдавать за результаты сайта |

### R-02. Ошибочные результаты из-за зависимости проверок друг от друга

| Поле | Описание |
| --- | --- |
| Риск: в чем суть? | Тестировщик начнет следующий сценарий с состоянием, оставшимся от предыдущего, либо примет предположение за требование; тип риска — организационный, связанный с подготовкой тестовых данных |
| Вероятность | Средняя — флажки меняют состояние после каждого действия, а сценарии используют разные начальные пары |
| Последствия | Ложные дефекты, пропущенные ошибки и невоспроизводимые результаты; требуется повторный прогон; влияние среднее, оценка угрозы `2 × 2 = 4` — средняя |
| Как не допустить | Для каждого сценария указать начальную пару, действия и ожидаемые переходы; перед запуском устанавливать и проверять нужные состояния. Ожидания по подписям и обновлению страницы явно связать с их основанием |
| Что делать, если наступил | Исключить недостоверный результат из итоговых метрик, восстановить предусловия и повторить проверку независимо. В отчете сохранить итоговый результат и пояснить причину повторного прогона; спорные ожидания вынести на уточнение |

## 5. Задание 3. Основные секции тест-плана

| № | Секция | Что размещается | Пример применительно к Checkboxes |
| --- | --- | --- | --- |
| 1 | Область тестирования | Функции и компоненты, включенные в проверку; исключения и причины исключений | Проверяются два флажка, независимость выбора, подписи, клавиатура, повторная загрузка и отображение. Другие разделы сайта, внешние ссылки, нагрузка и серверная безопасность исключаются как отдельные объекты и виды работ |
| 2 | Критерии качества | Измеримые условия приемки и завершения, допустимые дефекты | Все 5 Smoke и все 5 Critical Path должны пройти; открытых Blocker, Critical и Major — 0. Все 5 Extended должны быть выполнены, а оставшиеся Minor — описаны и явно приняты проверяющим; без такого решения работа не получает безусловную приемку |
| 3 | Оценка рисков | Вероятность, влияние, приоритет, профилактика и план действий при реализации риска | Учитываются недоступность внешнего окружения R-01 и неверные начальные состояния R-02. Более высокий приоритет имеет R-01, поскольку он блокирует весь браузерный прогон |
| 4 | Документация | Перечень документов, ответственные роли, момент подготовки и получатели | Тестировщик до прогона готовит этот план и уточняет проверки первой работы; во время прогона фиксирует результаты и дефекты. После завершения отчет и ссылки на дефекты передаются проверяющему |
| 5 | Стратегия тестирования | Методы, подходы, инструменты и последовательность проверок | Ручное тестирование методом черного ящика: Smoke → Critical Path → Extended; данные — состояния `0` и `1` и их сочетания. При провале Smoke дальнейшие зависимые проверки блокируются; после исправления BUG-01 выполняется повторная проверка подписей и регресс переключения по квадрату |
| 6 | Ресурсы | Программные, аппаратные, человеческие, временные и финансовые ресурсы | Нужны компьютер с Windows, браузер с клавиатурой, доступ в интернет, редактор Markdown и Git. Работу выполняет один тестировщик, проверяющий оценивает результат; учебный бюджет времени — 2 академических часа (90 минут), платные инструменты не требуются |
| 7 | Метрики | Показатели, формулы расчета, источники данных и целевые значения | Выполнение плана: `(Pass + Fail) / 15 × 100%`, цель 100%; успешность Smoke: `Pass Smoke / 5 × 100%`, цель 100%. Аналогичная цель для Critical Path — 100%; заблокированные и невыполненные проверки отдельно отражаются в отчете |
| 8 | Расписание и ключевые точки | Последовательность этапов, трудозатраты, результаты этапов и ответственные роли | Подготовка — 15 минут, Smoke — 10, Critical Path — 20, Extended — 20, оформление результатов — 15, резерв — 10. Ключевые точки: готовность плана, прохождение Smoke, завершение прогона и сдача отчета; ответственный за выполнение — тестировщик |

### Правила применения плана

**Критерии начала:** страница доступна, область проверки определена, начальные состояния и ожидания для каждого сценария подготовлены, браузер и клавиатура работают.

**Порядок выполнения:** сначала S-01–S-05. Если Smoke пройден, выполняются CP-01–CP-05, затем E-01–E-05. При проблеме среды или блокирующем дефекте зависимые проверки получают статус Blocked с указанием причины, а независимые допускается продолжить. После восстановления среды или исправления дефекта повторяются затронутые проверки.

**Критерии завершения:** у всех 15 проверок есть итоговый результат Pass или Fail, дефекты описаны, выполнены условия качества из секции 2 таблицы. Если остались Blocked или Not run, отчет можно сдать как отчет о незавершенном прогоне с причинами, но считать весь план выполненным нельзя. Известный BUG-01 требует повторной проверки; до исправления или принятия Minor-дефекта безусловная приемка не заявляется.

**Учет результатов:** Pass — ожидание выполнено; Fail — подтверждено несоответствие; Blocked — выполнению мешает внешняя причина или зависимость; Not run — проверка еще не начата. Каждая проверка учитывается в итоговых показателях один раз по последнему достоверному результату. Историю повторных запусков сохраняют отдельно.

Дополнительные метрики для итогового отчета:

| Метрика | Формула | Применение |
| --- | --- | --- |
| Выполнение плана | `(Pass + Fail) / 15 × 100%` | Показывает долю проверок с полученным результатом, цель — 100% |
| Успешность выполненных проверок | `Pass / (Pass + Fail) × 100%` | Рассчитывается только при наличии выполненных проверок; сама по себе не подтверждает полноту прогона |
| Успешность Smoke | `Pass Smoke / 5 × 100%` | Условие допуска к следующим уровням — 100% |
| Успешность Critical Path | `Pass Critical Path / 5 × 100%` | Условие приемки основных сценариев — 100% |
| Заблокированные проверки | `Blocked / 15 × 100%` | Для завершенного плана — 0% |
| Открытые существенные дефекты | Количество уникальных открытых Blocker, Critical и Major | Для приемки — 0; два проявления BUG-01 не считаются двумя отдельными дефектами |

Фактические значения нового прогона в этой работе не рассчитываются: результат задания — план. Процент найденных дефектов от их общего количества не используется, поскольку истинное число всех дефектов неизвестно. При нулевом знаменателе метрика обозначается как «не рассчитывается».

## 6. Выводы по работе

Разработан фрагмент тест-плана для Checkboxes на основе документации первой практической. Составлены 15 проверок трех уровней, оценены два риска разного характера и описаны восемь секций тест-плана с примерами для выбранного приложения.

Smoke позволяет быстро оценить минимальную работоспособность страницы, Critical Path проверяет законченные маршруты выбора и отмены, Extended охватывает подписи, клавиатуру, повторную загрузку и условия отображения. Выделение уровней помогает сначала проверить наиболее важное, а оценка рисков — подготовить действия на случай блокировок и недостоверных результатов.

Тест-план объединяет область работ, подход, ресурсы, критерии качества и порядок выполнения. Он дополняет чеклист и тест-кейсы: определяет организацию будущего прогона, тогда как тест-кейсы описывают отдельные действия и ожидания.

## 7. Ответы на контрольные вопросы

1. **Что подлежит тестированию?** Функции и компоненты, включенные в область тестирования на основании требований и рисков. В этой работе — открытие Checkboxes, два флажка, независимость их состояний, подписи, клавиатурное управление, повторная загрузка и отображение при изменении ширины и масштаба.
2. **Что такое тест-план?** Документ, который описывает и регламентирует тестирование: что и как проверяется, в какой последовательности, какими ролями, с какими ресурсами и по каким критериям оценивается результат. Его разрабатывают до прогона и уточняют по мере изменения условий.
3. **Как определить критерии качества?** Выбрать измеримые условия на основе требований, приоритетов и рисков, согласовать пороги и источник данных. Для Checkboxes установлены прохождение всех Smoke и Critical Path, выполнение всех запланированных проверок и отсутствие открытых Blocker, Critical и Major; оставшиеся Minor требуют отдельного решения о приемке.
4. **Что такое риски и как они оцениваются?** Риск — возможное событие, способное повлиять на качество или выполнение работ. Оценивают вероятность и последствия, определяют приоритет, профилактику и действия при наступлении; в этом плане применяется произведение баллов вероятности и влияния.
5. **Какие секции включает тест-план?** Область тестирования, критерии качества, оценка рисков, документация, стратегия тестирования, ресурсы, метрики, расписание и ключевые точки.
6. **Чем отличаются Smoke, Critical Path и Extended?** Smoke подтверждает минимальную работоспособность критичных функций; Critical Path проверяет основные законченные пользовательские сценарии; Extended добавляет редкие, граничные, негативные сценарии и альтернативные условия. Для чекбоксов негативные текстовые данные не нужны: редактируемых текстовых полей в выбранном модуле нет.
7. **Какие метрики используются для оценки качества тестирования?** Покрытие требований, выполнение плана, доля успешных проверок, успешность критичных сценариев, количество и серьезность открытых дефектов, доля блокировок. Покрытие требований рассчитывают как долю требований, связанных хотя бы с одной проверкой, среди всех требований в области; наличие связи не означает успешность проверки. Плотность дефектов используют только с определенной единицей размера, а долю всех найденных дефектов — только при известном общем числе дефектов.
8. **Какие ресурсы необходимы для проведения тестирования?** Программные средства и тестовые данные, оборудование и сеть, участники с определенными ролями, время и бюджет. Для этого модуля достаточно компьютера с Windows, браузера, клавиатуры, интернета, редактора Markdown, Git и одного тестировщика; для приемки нужен проверяющий.
